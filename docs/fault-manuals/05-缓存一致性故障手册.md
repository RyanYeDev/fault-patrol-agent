# 缓存一致性故障手册

> 知识标签：`fault-handbook` | 适用场景：数据不一致、缓存穿透/击穿/雪崩

## 故障现象

- 用户看到的数据与数据库不一致（如订单状态、商品信息、用户资料）
- 缓存命中率骤降，DB 压力激增
- 热点 key 过期瞬间大量请求打到 DB（击穿）
- 大量缓存同时失效导致 DB 压力雪崩

## 排查步骤

1. **Redis 检查（Redis 工具）**
   - 查看可疑 key：`redisGetKeyInfo('user:info:xxx')` —— 核对 TTL 与值
   - 查看字符串值：`redisGetString('order:status:xxx')` 与 DB 数据比对
   - 内存与慢日志：`redisMemoryInfo()` / `redisSlowLog(10)` 判断 Redis 自身是否异常

2. **指标分析（Prometheus）**
   - Redis 命中率：`rate(redis_keyspace_hits_total[5m]) / (rate(redis_keyspace_hits_total[5m]) + rate(redis_keyspace_misses_total[5m]))`
   - DB 连接数与慢查询：`mysql_global_status_threads_connected`、慢 SQL 指标
   - 接口错误率与延迟：业务接口 5xx / 99 分位耗时

3. **业务数据核对**
   - 将缓存值与 DB 记录比对，确认不一致范围与时间点
   - 查询数据变更日志，定位最近一次变更是否未同步缓存

4. **链路分析（Jaeger）**
   - 检索相关业务链路，确认更新路径（先删缓存还是先更新 DB）

## 常见根因

| 根因 | 特征 |
|------|------|
| 更新路径顺序错误 | 先删缓存再更新 DB 且更新失败，缓存回填旧值 |
| 缓存更新失败静默 | 双写缓存失败未重试，且无对账 |
| 缓存过期时间设置不当 | TTL 过短导致频繁击穿，或永不过期导致脏数据 |
| 无击穿保护 | 热点 key 过期瞬间并发回源打爆 DB |
| 多实例本地缓存叠加 | 本地缓存与集中缓存双重不一致 |

## 处置建议

1. 立即删除/刷新不一致的缓存 key（按影响范围批量处理）
2. 击穿场景：热点 key 加互斥回源（Redis setnx）或逻辑过期
3. 更新失败静默：修复双写失败重试，并开启异步对账
4. 雪崩场景：为批量 key 过期时间加随机抖动；核心数据启用多级缓存
5. 临时兜底：对 DB 保护性限流，防止雪崩扩散

## 预防措施

- 统一缓存框架：规范更新路径（先更新 DB 再删除缓存）、失败重试与对账
- 热点探测 + 互斥回源 + 逻辑过期兜底
- 缓存命中率、击穿次数纳入监控告警
- 核心缓存变更走 MQ 广播，避免多实例不一致
