# 支付回调故障手册

> 知识标签：`fault-handbook` | 适用场景：支付状态不同步、重复回调、回调丢失

## 故障现象

- 用户已支付但订单状态未更新（支付成功回调未处理）
- 同一笔支付收到多次回调，业务处理结果不一致
- 回调接口 5xx，支付渠道触发重复推送
- 回调处理延迟数分钟以上

## 排查步骤

1. **业务数据核对**
   - 查询支付流水：`SELECT * FROM payment_flow WHERE pay_order_id='xxx'`，核对回调次数（幂等计数）
   - 查询订单状态：`SELECT * FROM orders WHERE order_id='xxx'`，与支付渠道状态比对
   - 核对回调日志表：最后一次回调时间、处理结果、重试次数

2. **指标分析（Prometheus）**
   - 回调接口错误率：`rate(payment_callback_requests_total{status="5xx"}[5m])`
   - 回调处理耗时：`histogram_quantile(0.99, rate(payment_callback_duration_seconds_bucket[5m]))`

3. **MQ 检查（RabbitMQ 工具）**
   - 若回调经 MQ 异步处理：检查支付回调队列的 `messages_ready`（积压）与 `consumers`（消费者数）
   - 消费者异常退出会导致积压快速增长

4. **链路分析（Jaeger）**
   - 检索回调处理的慢链路，定位是渠道验签、DB 写入还是下游通知耗时

## 常见根因

| 根因 | 特征 |
|------|------|
| 幂等缺陷 | 回调重复处理导致状态错乱；幂等键粒度错误 |
| 验签失败 | 渠道密钥轮换后未同步，回调被拒 |
| MQ 消费者宕机 | 回调消息积压，状态迟迟不更新 |
| 事务内调用外部 | 回调处理事务内调用下游，事务拉长导致超时 |
| 渠道通知丢失 | 业务侧无主动查单兜底 |

## 处置建议

1. 先补状态：调用支付渠道主动查单接口，按渠道结果修正订单状态
2. MQ 积压时：扩容消费者实例、提高并发消费数
3. 修复幂等逻辑：以渠道流水号为幂等键，重复回调直接返回成功
4. 验签失败时：与渠道核对密钥配置，紧急切换备用密钥
5. 上线「主动查单 + 定时对账」兜底任务

## 预防措施

- 回调处理链路全异步 + 死信队列 + 重试退避
- 幂等处理标准化：渠道流水号唯一约束 + 状态机校验
- 定时对账任务比对渠道侧与业务侧支付状态
